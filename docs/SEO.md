# Stow search visibility

Status: first pass implemented. This file records what was audited, what changed, what is still
unverified, and the order of the remaining work. It covers Google Search only; store listings,
ads, and social are out of scope.

## The site, as deployed

| Item | Value |
| --- | --- |
| URL | `https://code-sharad.github.io/stow/` (GitHub Pages project site, one page) |
| Source | `landing/` on `main`, published by `.github/workflows/pages.yml` |
| Indexable pages | 1 (`landing/index.html`, ~970 visible words) |
| Synthetic | `landing/demo.html` (hero-animation dev page), `landing/HERO-DEMO.md` |
| Sitemap | `landing/sitemap.xml`, one URL |
| Robots | `landing/robots.txt` — see the caveat below |

Two hard constraints shape everything here:

1. **The host root is not ours.** Crawlers only read `https://code-sharad.github.io/robots.txt`,
   which 404s — Google never sees `landing/robots.txt`, so its `Sitemap:` line does nothing and a
   `Disallow` rule would do nothing either. (Verified with `curl`.) Control over robots, and real
   crawl directives, requires a custom domain.
2. **No link equity yet.** The page has no directory listings or editorial links; rankings for
   short commercial terms need links this site does not have. Long-tail problem queries and an
   honest alternative page are the realistic entry points.

## Audit findings

Severity is about expected impact on organic search, not code tidiness. Everything marked
"verified" was confirmed by fetching the live site or reading the shipped files.

### Critical — fixed

| Finding | Evidence | Fix |
| --- | --- | --- |
| The `<title>` carried no category or browser words (`Stow — Close the tabs. Keep the work.`), so it matched no query a searcher types. | Read from the live page; every ranking competitor puts category + browser in the title. | Title is now `Stow — a local-first Chrome tab manager` (39 chars). |
| The description was a slogan with no query language. | Live `<meta name="description">`. | Rewritten to 155 chars naming the category, the job, and the local-first promise. |
| The page never answered the questions it competes on: 721 words, no "save all tabs", no Chrome tab-group comparison, no import path for OneTab users. | Word and term counts over the rendered text. | New Questions section (`#questions`, six Q&As, 250 words) between features and privacy; hero lede now names the product ("Stow is a browser extension that saves the whole window as one searchable list"). |
| `demo.html` was served as a public, indexable HTML page (200, `text/html`), and `HERO-DEMO.md` as `text/markdown`. Both are dev artifacts. | `curl -I` on the live URLs. | `demo.html` is `noindex, follow`; `pages.yml` stages the artifact with `rsync --exclude demo.html --exclude HERO-DEMO.md`, so neither ships. |

### High — fixed

| Finding | Evidence | Fix |
| --- | --- | --- |
| The web font was the single largest resource: 351 KB, more than the HTML and CSS combined. | Resource timings: 351,680 B transfer, last to finish on a throttled connection. | Latin subset, 65,508 B (full 100–900 weight axis, all page glyphs, same rendering), regenerated by `scripts/subset-landing-font.sh`. |
| Structured data was thin: `SoftwareApplication` with no version, screenshot, or price flag, and no `FAQPage` for the questions the page answers. | JSON-LD read from the live page. | `SoftwareApplication` gained `applicationSubCategory`, `softwareVersion`, `isAccessibleForFree`, `inLanguage`, `screenshot` (a real capture), `sameAs`; `FAQPage` added and kept word-for-word in sync with the visible section. `installUrl` is deliberately omitted: there is no store listing to point at yet. |
| Sitemap had no `lastmod`, and no `max-image-preview` directive existed. | `landing/sitemap.xml`, `<head>`. | `<lastmod>` added; `<meta name="robots" content="index, follow, max-image-preview:large">`. |

### Medium — partly fixed, partly blocked

| Finding | Evidence | Status |
| --- | --- | --- |
| `robots.txt` at the host root does not exist, so the site's own robots file is inert. | `curl https://code-sharad.github.io/robots.txt` → 404. | Not fixable on `github.io`. Keep the file for correctness and move to a custom domain when the site gets one. |
| Duplicate URL `/stow/index.html` returns 200 next to `/stow/`. | `curl -I`. | Covered by the canonical; nothing else needed. |

| No external links. OneTab, Toby, Workona, and Session Buddy all have directory listings and reviews. | No link sources found in the repo or on the page. | Roadmap below; backlinks cannot be manufactured honestly in code. |

### Low — noted, not actioned

- `assets/icon.png` is 15.8 KB for a 24 px render; the hero fallback image is eager at 41 KB.
  Both are below the threshold where a fix changes anything measurable; revisit only with field
  data.
- `og:title` deliberately keeps the slogan while the `<title>` carries keywords. Social previews
  are read by people, not ranked; do not "fix" this.
- No breadcrumb markup: a single page has nothing to describe.

## Performance: what was measured, and what was not

Measured with Chromium (playwright-core) on an emulated Fast 3G profile (1.6 Mbps down, 750 kbps
up, 150 ms latency) with 4× and 8× CPU throttling, five runs per variant, medians compared.

- First Contentful Paint 1.3–1.6 s; Largest Contentful Paint equals FCP in every run, with the H1
  as the LCP element; DOMContentLoaded 1.7–2.4 s. A cold desktop visit now fetches ~232 KB of
  uncompressed bytes (HTML, two stylesheets, the demo module, font, hero fallback, icon) against
  ~518 KB before, almost all of the difference being the font.
- **No LCP claim.** An A/B of the 351 KB font against the 66 KB subset came out within run-to-run
  noise (±150 ms), and an ablation that removed the hero's fade-in changed nothing. The byte
  reduction is verified; a Core Web Vitals improvement is not.
- The real CPU cost is the scripted hero demo (36 KB of JS building a large DOM). If field data
  ever shows a problem, defer or split that module — not the font.

## Keyword map

Search volumes and keyword difficulty were not measured: no paid tool is in use here, and Google,
Bing, and DuckDuckGo all blocked automated SERP reads (consent/challenge pages). What follows is
grounded in Google Autocomplete suggestions, which show that a phrasing has real demand, and in
what competitors actually publish. Treat the ordering as a judgment call, not as data.

| Cluster | Intent | Evidence | Where it lands |
| --- | --- | --- | --- |
| chrome tab manager, tab manager extension, tab organizer chrome extension | Product discovery / commercial | Autocomplete returns all of these for "chrome tab" | Title, description, hero lede, questions |
| save all tabs chrome, save all tabs chrome extension, how to save all tabs in chrome for later / before closing | Problem solving | Dense autocomplete, plus Workona's dedicated guide | Questions Q2, hero lede |
| bookmark all tabs chrome, save open tabs chrome for later | Problem solving, adjacent tool | Autocomplete | Questions Q2 (names Chrome's own shortcut honestly) |
| difference between tab groups and tab manager | Informational | Autocomplete for "chrome tab groups" | Questions Q3 |
| onetab alternative, best onetab alternative, open source tab manager | Commercial investigation | Autocomplete; Workona and Session Buddy both target it | Roadmap: a comparison page |
| private / local / offline tab manager, tab manager without cloud | Differentiation, near-zero demand | Autocomplete returns little or nothing | Used as trust copy, not as a target keyword |

Deliberately not targeted: "browser workspace extension" (Citrix, LSEG, and Devolutions own that
phrasing), "tab session manager" (Stow's UI does not call lists sessions; forcing the word would be
dishonest), and anything implying cloud sync, collaboration, or AI.

## Competitors

| Site | Title pattern | Words on page | Content assets |
| --- | --- | --- | --- |
| OneTab | category + browser + benefit | 526 | none; no sitemap |
| Toby | "The Best Way to Organize Your Tabs" | 1,703 | blog, 57 URLs |
| Session Buddy | brand only | 882 | none |
| Workona | "Tab Manager \| Tab Organizer for Chrome, Edge, & Firefox" | 603 | 158 URLs: comparison, how-to, review, and use-case pages |
| Tab Manager Plus | brand + benefit | 187 | none |

What that means: the category is won by one strong page plus a small set of honest comparison and
how-to pages, and Workona owns the "save all tabs" and "alternative" intents outright. Stow cannot
out-write Workona from a `github.io` subpath; it can be the most accurate page about saving tabs
locally and the best-documented OneTab alternative, which is a narrower and winnable claim.

## Roadmap

Ordered by expected effect per unit of work. P0 items are done or need the owner only.

1. **P0 (file added, owner action left):** Search Console verification. `landing/
   google3d833a44d7eced00.html` is in the repo and the publish step copies it, so after the next
   deploy the file is served at the URL-prefix property. Then: click **Verify**, submit
   `sitemap.xml`, run URL Inspection on the page, and record the baseline (impressions, clicks,
   average position, indexed status) in this file. The file only verifies the URL-prefix property
   `https://code-sharad.github.io/stow/`; a Domain property is verified by DNS TXT instead and
   cannot use this file. Nothing can be monitored before this exists.
2. **P0 (done):** title, description, questions section, JSON-LD, sitemap `lastmod`, `noindex` and
   publish exclusion for dev files, font subset.
3. **P1:** one comparison page — `/stow/compare/onetab/` or similar, written as a fair table
   (Stow imports OneTab exports; OneTab has a longer track record and its own memory claims).
   This is the highest-intent query cluster Stow can honestly answer.
4. **P1:** one how-to page for "save all tabs in Chrome", showing the shortcut, Chrome's bookmark
   route, and Stow, with the same honesty as the FAQ. Only if it can be better than Workona's.
5. **P1:** a custom domain. It buys a root `robots.txt`, a real brand URL in results, and a place
   for link equity to accumulate; it is also the prerequisite for anything beyond a single page.
6. **P2:** links: GitHub repo topics and README link, AlternativeTo listing, open-source and
   browser-productivity awesome lists, genuine comments where tab clutter is discussed. No paid
   links, no PBNs, no automated outreach.
7. **P2:** extend `scripts/check-landing.mjs` with a link checker once there is more than one page.

## Validation

```sh
pnpm check:landing          # layout, axe, no-JS, and the SEO assertions in scripts/check-landing.mjs
pnpm lint                   # biome, includes the checker and the subset script's callers
./scripts/subset-landing-font.sh   # rebuilds landing/assets/inter-var.woff2 reproducibly
```

The checker now fails on: title or description length and missing category words, a non-absolute
canonical, missing `robots`, a broken `og:image`, a `twitter:card` that is not
`summary_large_image`, JSON-LD that does not parse, a `SoftwareApplication` missing its category or
price, a `FAQPage` whose questions drift from the visible ones, a sitemap that lists anything other
than the canonical URL or lacks `lastmod`, a `robots.txt` without its sitemap line, an indexable
`demo.html`, a skipped heading level, a duplicate id, or a `#anchor` with no target.

Outside the repo: Schema Markup Validator and Rich Results Test on the deployed URL, PageSpeed
Insights for field data once it exists, and Search Console URL Inspection after each deploy.

## Monitoring

There is no analytics on the page by design (the extension has no network code, and the site keeps
the same promise), so Search Console is the only source: impressions and clicks by query, average
position for the clusters above, indexed-page count, sitemap fetch status, and any manual action.
Record the first snapshot here when the property is verified; without it, any statement about
rankings would be a guess.
